Connectors

Connectors are integrations with external services that extend Aria's capabilities and power agent functionality. Each connector is defined in the connectors table and linked to users via user_connectors.

Connector Types

API Key Connectors

The user provides an API key (and optionally other config values). Keys are stored in user_connectors.config and used directly in tool calls.

Examples: Anthropic, Google Gemini, SCX AI, Substack.

OAuth Connectors

The user completes an OAuth flow. Tokens are stored in connector_tokens and automatically refreshed via OAuthService::getValidToken(). OAuth flows are handled by ConnectorOAuthController.

Examples: Microsoft 365, Gmail.

RouteAction
GET /connectors/{slug}/authorizeStart the OAuth redirect.
GET /connectors/{slug}/callbackReceive the token after consent.
POST /connectors/{slug}/disconnectRevoke the user's token.

Admin management

Admins manage the connector catalogue at /admin/connectors and assign connectors to users at /admin/users/{user}/connectors.

Tool Definitions Format

A connector's tool_definitions field is a JSON array of tool schemas in Anthropic's tool format. When Aria builds its tool list it merges definitions from all active connectors. The internal fields _connector_slug and _connector_config are stripped before being sent to any LLM.

[
  {
    "name": "tool_name",
    "description": "What this tool does.",
    "input_schema": {
      "type": "object",
      "properties": {
        "param": { "type": "string", "description": "..." }
      },
      "required": ["param"]
    }
  }
]

API Gateway & Keys

The API Gateway lets external scripts call a user's connected services programmatically via a single authenticated proxy or unified tool invocation endpoint, without managing upstream OAuth tokens or API keys directly.

EndpointPurpose
GET /api/gateway/toolsUnified gateway discovery manifest: returns all available tools and their input schemas.
POST /api/gateway/invokeUnified gateway invocation: run any tool by name. The gateway routes it to the owning connector.
GET /api/gateway/v1/models
POST /api/gateway/v1/chat/completions		OpenAI-compatible gateway endpoints. Allows OpenAI clients to interact with active connectors executed server-side.
ANY /api/gateway/{connector_slug}/{path?}Bearer-authenticated proxy. Injects the user's stored OAuth token or API key and forwards the request.
GET / POST / DELETE /api/gateway/keysSelf-service key management (JSON API), session-authenticated.
/dashboard/profile#api-keysSelf-service key management (dashboard UI) — the primary way users create/revoke their own keys.
/admin/api-keysAdmins issue a key on behalf of any user.

OpenAI-Compatible Gateway Endpoints

You can point any OpenAI-compatible client at the base URL https://apispi.com/api/gateway/v1 using your gateway key (gw_xxxxx):

from openai import OpenAI

client = OpenAI(base_url="https://apispi.com/api/gateway/v1", api_key="gw_xxxxx")
resp = client.chat.completions.create(
    model="claude-sonnet-4-6",
    messages=[{"role":"user","content":"Search my connectors and summarize"}],
)

How it works: The request runs through the same agentic engine Aria uses (runAgentLoop) — the caller's active connectors are auto-injected as tools and executed server-side — and the final message comes back in OpenAI's chat.completion shape (id, object, choices[].message, usage). It also adds a non-standard apispi.tool_calls field so you can see which connector tools ran.

v1 scope / limitations (worth knowing):

  • Non-streaming only. stream:true is rejected — SSE is the planned follow-up.
  • Model maps to Anthropic. A claude-* model passes through; anything else (e.g. gpt-4o) falls back to the platform default. /v1/models advertises the Claude models.
  • Client-supplied tools are ignored — the gateway uses your connectors as the tool set and runs them itself (its value-add), rather than returning tool_calls for client-side execution.
  • max_tokens from the request isn't honored yet (fixed 1024 in the loop).
  • Validation/auth/throttle errors now render as JSON (forced Accept: application/json in GatewayAuth, so clients without that header still get OpenAI-style error objects).

Keys are prefixed gw_, hashed with SHA-256 at rest, and shown in full only once at creation. A key is not scoped to specific connectors — it works against any connector the owning user has actively connected. There is currently no rate limiting on gateway/proxy requests. Every proxy call is logged to connector_usage_log (user, connector, tool/path, status, result count, error message) and reviewable at /admin/token-usage.
