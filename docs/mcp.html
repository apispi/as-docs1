MCP & A2A

ApiSpi speaks the Model Context Protocol in both directions: it is an MCP server (any MCP client can use your connected tools) and it consumes remote MCP servers and A2A agents as connectors.

MCP Server

POST https://apispi.com/api/gateway/mcp

McpController is a stateless Streamable HTTP MCP server speaking JSON-RPC 2.0 over a single POST endpoint — no server-side session. The caller's Bearer credential (via the gateway.auth middleware) is the only identity needed, so every request is self-contained. It exposes the same tool set as the unified gateway and Aria's own tool loop (RunsAgentTools::buildTools()), so MCP clients get your connectors without ApiSpi re-implementing each integration as an MCP server.

Tool Calls & Governance

  • tools/list returns each tool's name, description, and inputSchema — the candidate set already filtered by governance (kill switch, sovereignty, disabled tools; see Tool Selection).
  • tools/call results carry a JSON content text block for every client plus structuredContent for 2025-06-18 clients, with isError set on failures. An unknown/unavailable tool returns an in-band tool error, not a protocol error.
  • Governance can require approval: a call may return status approval_required — the server's instructions tell the model to inform the user and retry after approval.

Authentication

Two options, both resolved by gateway.auth:

  1. Gateway API key — Authorization: Bearer gw_… (see API Gateway). The prefix-less form is also accepted.
  2. OAuth — for MCP clients that expect an OAuth flow (e.g. adding ApiSpi as a Claude connector). The access token issued is a gateway API key under the hood.

Unauthenticated requests get a 401 with a WWW-Authenticate header pointing at the protected-resource metadata, which lets clients bootstrap the whole flow automatically:

EndpointPurpose
GET /.well-known/oauth-authorization-serverServer metadata: authorization_code grant only, PKCE S256 only, scope tools. Served as static discovery documents.
GET /.well-known/oauth-protected-resourceProtected-resource metadata (RFC 9728).
POST /oauth/registerDynamic client registration (RFC 7591) — public clients only, no client secret.
GET/POST /oauth/authorizeSession-authenticated consent screen.
POST /oauth/tokenExchanges the code + PKCE verifier for an access token (a gateway key).

Connecting a Client

Claude Code (API-key auth):

claude mcp add apispi --transport http https://apispi.com/api/gateway/mcp \
  --header "Authorization: Bearer gw_<your-key>"

Claude Desktop / claude.ai custom connector (OAuth): add https://apispi.com/api/gateway/mcp as a remote MCP server — discovery, registration, and consent happen automatically; approve access when the ApiSpi consent page appears.

Wire Logging (Debug)

Setting MCP_WIRE_LOG=true enables the McpWireLog middleware on the whole MCP/OAuth surface: one entry per request/response pair (method, URL, status, UA/Origin/Accept headers, truncated bodies) written to storage/logs/mcp-wire.log. Anything shaped like a gateway key is masked before logging. It is intended as a temporary handshake-debugging aid — leave it disabled in normal operation, since it logs request bodies.

MCP Client — Remote Servers as Connectors

McpClientService lets ApiSpi consume any remote MCP server as a first-class connector, so its tools appear in Aria's tool loop and the gateway exactly like native ones:

  • Registration — an admin adds the server at /admin/connectors/mcp/add (URL + optional bearer token). The connector rows gain transport, mcp_url, and an encrypted mcp_auth_token.
  • Discovery — discoverTools() performs initialize then tools/list and normalises the result into the same tool_definitions shape native connectors use. Re-import any time with POST /admin/connectors/{connector}/mcp/refresh.
  • Execution — an Aria/gateway tool call is translated into an MCP tools/call; text content is surfaced, structuredContent is preferred when present, and isError results are returned as failures so the model sees them as such.
  • Transport — stateless Streamable HTTP via RemoteJsonRpc, bearer-token auth. OAuth-secured remote MCP servers are not yet supported.

A2A — Agent-to-Agent

The same pattern exists for the A2A protocol:

  • As a server — POST /api/a2a (A2AController), with a published agent card at GET /.well-known/agent-card.json so external agents can discover ApiSpi and exchange tasks with it.
  • As a client — A2AClientService consumes external A2A agents as connectors (a2a_url + encrypted a2a_auth_token), registered at /admin/connectors/a2a/add with an agent-card refresh at POST /admin/connectors/{connector}/a2a/refresh.
