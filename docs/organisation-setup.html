Organisation Setup

Rolling ApiSpi out to a team, not just yourself? This guide is for the person wearing the administrator hat — it sets up identity, org-wide governance, and monitoring so your users get a governed AI workspace on day one.

Before you start: you need an ApiSpi account with administrator access (the ApiSpi team enables this when your organisation signs up — contact sales@apispi.com). Individual users don't need any of this page; point them at Getting Started instead.

1. Plan Your Rollout

Decide three things up front — everything else in this guide implements them:

DecisionQuestions to answer
Who can use AI, and for what?Which teams get access? Which agents and connectors are appropriate? Any topics that must be off-limits?
Which models are acceptable?Bring-your-own provider keys or platform credit? Any data-sovereignty constraints (e.g. no Chinese-hosted providers)?
What must be auditable?Who reviews guardrail events? Do prompt/response logs need to reach your SIEM?

2. Set Up Identity & Sign-In

  1. Each team member registers with their work email at apispi.com/register — they start on the standard 7-day trial and inherit your org policy automatically
  2. If your organisation uses Microsoft Entra ID (Azure AD), ask the ApiSpi team to configure SSO — "Continue with Microsoft" then appears on the login page, and role-based access (who may use which models and agents) follows your directory. Entra SSO also enables Aria in Microsoft Teams: a native bot on the same governed engine, mapping each Teams user to their ApiSpi account
  3. Users verify their email on sign-up, and can add passkeys (WebAuthn) for phishing-resistant sign-in
  4. From the admin area you can review users, assign or revoke agent subscriptions, and issue gateway API keys on a user's behalf — each key can be scoped to a tool-access mode, a connector allowlist, and a daily spend cap

3. Write the Org Policy

The org policy is the single source of truth every user inherits. In the admin Governance page, work top to bottom:

ControlWhat to set
Policy notesFree text injected into every Aria conversation (up to 50,000 characters) — your acceptable-use rules, tone requirements, disclaimers. Write it like instructions to a diligent employee.
Blocked keywordsTopics that must never be discussed. Choose the action — block (reject), redact (mask), or warn — and the scope (user input, AI output, or both). Enable whole-word matching to avoid false positives.
Token limitsA daily per-user token cap keeps spend predictable. Users can set stricter personal caps, never looser.
Data sovereigntyBlock connectors by country. Model providers carry country labels (DeepSeek, Qwen, Z.ai, Moonshot are labelled China), so one rule removes them from every user's tool set.
Tool accessRead-only drops all state-changing tools (send email, create files); approval mode pauses before actions and caps autonomous runs (max actions, time budget). Start restrictive, loosen deliberately.
Access windowsOptionally restrict AI use to business hours/days.
Injection detection & alertsTurn on prompt-injection detection and admin alerts so attempts surface immediately.
These controls are enforced on every path — Aria chat, the LLM Gateway, MCP clients, scheduled runs — not just the dashboard. Users see an honest explanation when something is blocked, which cuts support tickets.

4. Curate Connectors & Agents

  1. Review the connector catalogue and disable anything your organisation shouldn't use — a disabled connector disappears from every user's catalogue
  2. If you have internal MCP servers or A2A agents, register them as connectors so their tools become available (and governed) platform-wide — see MCP & A2A
  3. Assign agents to users, or let users activate agents into their own plan slots

5. Monitor & Audit

  • Token usage — per-user, per-model consumption with a daily chart (including which client made each gateway request), so cost surprises don't happen
  • SIEM/webhook export — stream governance events to Splunk, Elastic, Sentinel/Defender, or any webhook in real time: signed with a rotatable secret, test deliveries, and automatic retries with delivery visibility
  • Governance digest emails — a per-org summary of guardrail and usage activity, delivered by email
  • Maker-checker — once you have a second administrator, enable dual-admin approval so sensitive changes (policy, firewall rules, admin grants, key-scope widening, retention) need a second pair of eyes
  • Governance audit — every guardrail event (keyword blocks, injection attempts, moderation flags) in one reviewable log
  • Connector activity — each tool execution is logged: who, which connector, which tool, success or error
  • Emergency stop — the org-level kill switch halts all connector tool traffic at once, across every surface; users are told an emergency stop is active rather than seeing cryptic errors. Engaging it twice is safe (idempotent)

6. Scale Up: Teams & Stronger Isolation

  • Workspaces — shared team chat spaces with one Aria conversation per workspace, per-member AI toggles, and the same token limits
  • On-Prem Appliance — when policy-level control isn't enough, the appliance enforces the same governance at a network choke point: all LLM traffic through your DMZ, direct egress to AI providers blocked at the perimeter, SSO/RBAC via your directory, audit logs streamed to your SIEM (Essential Eight / ISM / PSPF-aligned)
